# 功能检查与完善建议（2026-11-05）

本次检查基于本地版本 `78ab86c`，结合现有教师端、学生端、API、数据库与评分算法实现。线上入口为 <https://111.228.49.178/algorithm/>。

通过 SQLite 在线备份接口复制数据库，在临时目录中启动独立 HTTP 服务后复现边界场景。新账号、异常评分、作业及提交均只写入临时数据库。线上仅登录演示账号并读取题目详情，未调整课程、作业、评分或程序代码。

结论：平台已经具备课程要求的大部分模块，但作答流程、课程权限、评分有效性和异常处理之间仍有断点。应先修这些问题，再补新功能。

## 一、应优先修复的问题

### 1. 主观题作答没有传递作业上下文（P1）

- 学生在作业卡片点「去完成」，链接仅为 `#/problem/{id}`，没有作业编号。
- `loadProblem()` 只读取题目详情。线上主观题 20 的响应中，没有 `assignment_id`、`assignment_ids`、`my_subjective`。
- 提交主观题时页面从这几个字段寻找作业编号，结果为空，后端会返回「缺少作业或题目」。编程题也会丢失所属作业，影响作业统计和截止规则。
- 页面虽然写有「更新提交」，却没有加载原作答来填回输入框，修改体验也不完整。
- 建议：从作业进入题目时携带并校验作业编号；从题库进入时明确区分自由练习与作业提交；主观题加载原文并提供草稿保存。
- 位置：`frontend/js/pages/student.js` 的 `loadProblem()`、`renderStudentAssignment()`；`frontend/js/pages/problem.js` 的两类作答面板；`backend/api.py` 的题目详情接口。

### 2. 课程之间的访问权限不完整（P1）

- 在副本中新注册另一位教师，其 `/api/problems/{id}` 能读取原教师题目，`PUT` 同一地址也能修改原课程题目，均返回 HTTP 200。
- 新教师调用 `/api/users` 能取得全站用户列表，复现时为 52 人。
- 新注册但未加入课程的学生，访问题目和作业列表仍拿到原课程的 29 道题、11 次作业。原因是没有课程时跳过了 SQL 课程筛选。
- 建议：按每个资源所属课程验证成员身份与教学权限；无课程账号返回空列表；对指定资源进行检查，不能只检查全局角色。
- 位置：`backend/api.py` 的课程选择、用户、题目、作业、提交、评审接口；`backend/api_ext.py` 的分析和通知接口。

### 3. 草稿与教师参考答案可能被学生读取（P1）

- 副本中创建草稿作业，学生列表和详情均可读取，详情返回 HTTP 200。
- 在副本题目中加入参考答案标记，学生获取作业详情后，`problems[].solution` 中包含该标记。题目详情接口已隐藏此字段，作业详情没有执行同样的过滤。
- 本地迁移数据库目前没有已填充的 `solution`，因此此项用临时标记验证，不能据此声称已有真实答案泄露。
- 建议：学生侧过滤草稿，作业详情复用统一题目序列化，排除参考程序、生成指纹等教师字段。
- 位置：`backend/api.py` 的 `assignment_detail()`、`api_assignments()`、`api_assignment()`。

### 4. 截止时间、作业状态与题目归属未形成提交约束（P1）

- 对已关闭且截止于 2020 年的作业，主观题提交仍返回 HTTP 200。
- 作业仅包含编程题 A，仍能提交不属于该作业的主观题 B，返回 HTTP 200。
- 代码提交接口也缺少相同的状态、开放时间、截止时间和题目关联检查。
- 建议：后端统一校验开放状态、开始与截止时间、课程成员、题目类型及作业题目关联；教师延长截止后再允许补交。自由练习独立处理。
- 位置：`backend/api.py` 的 `api_submit()`、`api_subjective_submit()`。

### 5. 互评可以接收非法分数及无效时长（P1）

- 副本中向未确认发布、已过互评截止时间的任务提交 `{"not_a_rubric_key": 1000}`，后端接受并返回总分 1000。
- 同次提交的评审时长为负数，也被写入数据库。
- 前端滑块的范围无法替代服务端校验。前端还把评审时长强制提高到至少 20 秒，会掩盖秒评行为。
- 建议：后端验证评分项与细则完全对应，各项为有限数值且落在 0 至该项满分内；校验任务发布与截止状态；记录服务端开始和提交时间，前端原样显示真实用时。
- 位置：`backend/api.py` 的 `api_submit_review()`；`frontend/js/pages/student.js` 的 `renderReviewTask()`。

### 6. 学生能提前取得聚合分，匿名接口包含真实作者 ID（P1）

- 对互评截止于 2099 年的临时提交，主观题列表返回最终分 88 及聚合方法分数，其中还包含同题其他作者分数。
- 详情虽然把 `final_score` 清空，但 `methods` 仍返回 88，`review_published` 为 false。
- 学生的「我的互评」列表保留 `author_id`。匿名编号使用公开的固定公式计算，结合班级名册返回的用户 ID，可关联到具体姓名。
- 建议：统一结果发布判断，列表、详情、作业卡片、统计和报告同步执行；学生侧方法分数只返回自己的；匿名标识按作业和轮次生成，不向评审者返回真实作者 ID。
- 位置：`backend/api.py` 的 `anon_label()`、`api_subjective_list()`、`api_subjective_detail()`、`api_my_reviews()`。

### 7. 教师降权没有影响最终分数（P1）

- 建立两位评审者分别给 10、90 分的临时场景，聚合结果为 50。
- 教师把高分评审者权重改为 0.01，数据库保存成功，重新读取评分结果仍为 50。
- 原因：异常处理修改 `allocations.weight`，聚合入口没有把该权重传给算法，结果页面又独立重新计算。
- 建议：明确教师权重如何与算法可信度组合；统一聚合入口和展示结果；调整后重算并记录操作前后的分数、理由与操作者。
- 位置：`backend/api_ext.py` 的 `api_anomaly_handle()`；`backend/api.py` 的 `_load_review_context()`、`api_aggregate()`、`api_review_results()`；`backend/algo/aggregation.py`。

### 8. 重新分配后旧评分继续残留（P1）

- 在已有两份完成评分的临时作业中执行重新分配，旧任务被删除，但两条评分仍引用已删除任务。
- 聚合按作业和题目加载评分，因此旧评分仍可能计入新一轮结果。
- 建议：引入明确轮次或在事务中完成旧轮次归档与新轮次创建；只聚合当前有效轮次；保留教师已处理异常的审计记录。
- 位置：`backend/api.py` 的 `api_allocate()`、`_load_review_context()`、`api_aggregate()`。

## 二、数据与展示一致性问题

### 9. 题目通过率可能超过 100%（P2）

- 同一学生重复获得 Accepted 后，接口把「通过提交次数」除以「尝试人数」。
- 副本复现值为 1.7907，即 179.07%。
- 建议：人数通过率使用去重通过人数 / 去重尝试人数，提交通过率另用 Accepted 提交次数 / 总提交次数。
- 位置：`backend/api.py` 的 `api_problems()`。

### 10. 新提交的测试点明细存储与重测不同（P2）

- 普通提交后，结果 JSON 有 10 个测试点，`test_results` 表却为 0 条；单条重测会写入该表。
- 学生历史详情已有 JSON 兜底，因此不能说该页面一定空白；代码互评读取表中记录，新提交可能缺少测试点信息。
- 建议：提交与重测复用同一份结果落库逻辑，提供一致的详情结构。
- 位置：`backend/api.py` 的 `api_submit()`、`api_rejudge()`、`api_review_task()`。

### 11. 作业统计可能把其它作业或练习记录算作本次完成（P2）

- 学生工作台按题目和用户判断通过，不限定作业；教师进度接口在本作业没有记录时，回退到全局题目提交。
- 同一道题安排多次时，学生以前练习通过可能被当成本次已完成。这与「允许使用历史代码组织互评」需要分开表达。
- 建议：默认按本次作业统计；复用历史提交作为显式选项，并在页面标注来源。
- 位置：`backend/api_ext.py` 的 `api_assignment_progress()`、`api_dashboard_student()`。

### 12. 批量重测结果可能与历史明细矛盾（P2）

- 批量重测仅更新 verdict、score、time、memory，不更新编译信息、结果 JSON 和测试点表；同时固定只处理前 80 条，响应没有剩余条数。
- 建议：复用单条重测并提供进度、失败数量、剩余数量，防止界面显示新判定却保留旧明细。
- 位置：`backend/api.py` 的 `api_rejudge_assignment()`。

前 10 个编号共包含 13 个独立复现场景；第 1 项由线上只读响应与前端调用链确认，第 11、12 项为代码路径分析，尚未进行完整页面场景复现。

## 三、建议补充的实际使用功能

1. **账号维护**：所有角色修改自己的密码；教师重置本课程学生密码；改密后失效旧会话。当前只有注册、登录、退出和公开资料编辑。
2. **作答草稿与恢复**：主观题自动保存、重新打开回填；代码草稿按账号、题目、语言区分，避免同一浏览器切换账号或语言时覆盖。
3. **成绩复核流程**：学生发起成绩申诉，教师查看原评分及算法结果，填写处理理由，支持人工最终分与操作历史。
4. **通知管理**：服务端保存已读状态，支持跨设备同步；「全部通知」增加分页，当前接口最多返回 30 条。
5. **课程切换**：前端已有 `courseId` 状态，但大部分接口调用没有使用该状态，后端默认取第一门课程。应让教师和学生能明确切换活动课程。
6. **备份恢复**：部署已有一次性备份，建议增加数据库和课件定时备份、保留策略与恢复演练，避免旧服务器欠费时再次依赖本地旧快照。

这些是新增能力建议，不与已复现缺陷混为已实现功能。

## 四、实施顺序与验收

第一批：课程权限、作业上下文、提交规则、互评分数校验、结果发布与匿名标识。

第二批：教师降权实际参与聚合、重新分配轮次、评分结果与明细一致性、正确统计通过率。

第三批：改密与重置、作答草稿、成绩申诉、多课程切换、通知分页与备份。

验收应覆盖：未入课学生、另一门课教师、草稿作业、未开始/已截止作业、重复安排同一题、非法评分、未公布成绩、重新分配、教师降权前后差异。现有「正常流程返回 200」的检查无法替代这些场景。

## 五、2026-11-06 修复记录

上述第 1–12 项已修复，并增加临时数据库上的 HTTP 回归测试，覆盖跨课程、作业归属、原文回填、截止时间、非法评分、成绩发布、匿名标识、教师权重、轮次归档、批量重测和统计隔离。重新分配先归档旧轮次，再清理旧评分；教师权重参与 EM 与加权均值，权重为零的评审不参与最终分。

新增账号改密、教师重置本课程学生密码及旧会话失效、主观题浏览器草稿、按账号/语言/作业保存代码草稿、活动课程切换、通知接口分页。历史代码互评升级时固定原提交来源，不将历史练习回填成本次作业提交；新轮次仅选择本次作业的代码。

验证：66 项算法测试、21 项 HTTP 流程回归、21 个前端模块语法检查、15 项渲染交互检查，以及数据库副本上的 168 项完整接口检查均通过。复杂度实测属于可选检查，本次接口检查未运行该项。HTTP 回归已加入 GitHub Actions。

成绩申诉、跨设备通知已读同步、定时备份仍属于后续功能；此次部署提供升级前数据库及代码备份。
